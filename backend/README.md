# Backend — Database Schema

## What's here

- `app/models/` — SQLAlchemy models for the 7 core entities: Instructor,
  EnvironmentDefinition, Requirement, Student, Enrollment, CheckRun,
  CheckResult.
- `app/database.py` — engine/session setup, reads `DATABASE_URL` from env.
- `alembic/` — migrations. `versions/0001_initial_schema.py` creates all
  tables + Postgres enums.

## Run it locally

1. Start Postgres (from the project root, one level up):
   ```
   docker compose up -d postgres
   ```

2. Set up the backend:
   ```
   cd backend
   python3 -m venv venv
   source venv/bin/activate   # Windows: venv\Scripts\activate
   pip install -r requirements.txt
   cp .env.example .env
   ```

3. Apply the migration:
   ```
   export $(cat .env | xargs)   # or use python-dotenv / your shell's env loading
   alembic upgrade head
   ```

   This creates all 7 tables plus the `check_run_status`, `check_result_status`,
   and `action_taken` Postgres enum types.

4. Verify:
   ```
   psql postgresql://postgres:postgres@localhost:5432/student_env_platform -c "\dt"
   ```
   You should see: instructors, students, environment_definitions,
   requirements, enrollments, check_runs, check_results.

## Making schema changes later

After editing a model in `app/models/`, generate a new migration:
```
alembic revision --autogenerate -m "describe your change"
alembic upgrade head
```
Always review the autogenerated file before applying — Alembic is good but
not perfect, especially with enum changes.

## Next step

This is Phase 1 (schema only) of the platform. Phase 2 is the FastAPI
backend that reads/writes through these models.

## Phase 2 — Running the API

Once the migration (above) has been applied against Postgres:

```
uvicorn app.main:app --reload
```

Then open **http://127.0.0.1:8000/docs** for interactive API docs (Swagger UI) —
you can try every endpoint directly from the browser.

### Core endpoints

| Method | Path | Purpose |
|---|---|---|
| POST | `/instructors` | Create an instructor |
| POST | `/environment-definitions` | Create an environment + its requirements |
| POST | `/students` | Create a student |
| POST | `/enrollments` | Enroll a student in an environment definition |
| POST | `/check-runs` | Agent submits a check run + per-requirement results |
| GET | `/students/{id}/status` | A student's compliance across all their environments |
| GET | `/environment-definitions/{id}/compliance` | Instructor-facing rollup across all enrolled students |

### A note on `requirements.txt` versions

`fastapi` and `starlette` are pinned to `0.135.0` / `1.3.1`. This isn't
arbitrary:

- The original pin (`0.115.6` / `0.41.3`) was chosen because letting pip
  resolve to the latest `fastapi` at the time pulled in a `starlette`
  release that silently broke route registration (`include_router` added
  no routes, no error).
- That original `starlette==0.41.3` was later flagged by Snyk with 4
  high-severity CVEs (ReDoS, SSRF, resource exhaustion, name resolution) —
  all fixed in Starlette 1.0+.
- Jumping straight to the latest `fastapi` (`0.141.1` at the time) to get
  Starlette 1.x reproduced the *exact same* silent route-registration bug
  as before (with `starlette==1.6.0`) — a real, reproducible
  incompatibility between that specific pairing, not a fluke.
- `fastapi==0.135.0` / `starlette==1.2.1` was the first confirmed-working
  fix (found by testing versions between the two known-bad points),
  cutting Snyk's findings from 4 to 2 -- but Snyk still flagged 2 remaining
  CVEs in `starlette@1.2.1` (resource allocation limits, name resolution),
  fixed in `1.3.1`.
- `starlette==1.3.1` was then re-tested against `fastapi==0.135.0`
  specifically (not assumed compatible just because 1.2.1 was) — confirmed
  working: correct route count (21), and the full instructor → environment
  → student → enrollment → check-run → status/compliance flow verified via
  real HTTP calls against Postgres, zero server errors. This resolved all
  4 originally-flagged CVEs.

**If you ever bump these versions again**, don't just trust that it
installs — re-run the check below (route count) and the end-to-end smoke
test further down before trusting the result. This specific dependency
pairing has broken silently multiple times already.

```
python -c "from app.main import app; print(f'{len(app.routes)} routes registered')"
```
Should print `21` (or more, if new endpoints have been added since). If it
prints something close to `5`, routing is broken the same way it was before.
